# Troubleshooting

Run installed CLI `doctor --json`. Separate configuration, service health, bridge connectivity, usable caller context, and actual host delivery. Preserve durable watches and outgoing receipts while diagnosing.

| Observation | Action |
| --- | --- |
| `needsAccess`, `EPERM`, `EACCES` | Use the host's normal permission escalation for the authorized local pipe operation. Do not weaken global sandbox policy or repeatedly restart a running desktop. |
| `needsService` | Run installed CLI `service status`, then `service start` if stopped. Inspect `watch-service.log` for startup/worker errors; the login entry (VBS, LaunchAgent, or XDG autostart file) and stable launcher must remain managed and intact. |
| Missing token/unreachable desktop bridge | Codex desktop must load its bridge MCP configuration. Running `relay-server.mjs` in a normal shell cannot supply the private app tools environment. Follow the specific reload requirement without automatically focusing/restarting the app. |
| `appPipe:false` | The bridge lacks the desktop context or its host version changed. Verify configuration and compatibility; do not invent a pipe address. |
| No usable Codex caller | Ask the user to activate an existing chat; a user message may be needed by that Codex version. Do not send an unsolicited message to establish context. |
| Codex desktop-mode wake cannot address an unloaded/related supervisor | For authorized unattended follow-up, configure explicit `mode:"queue"` with a verified absolute Codex CLI that supports `queue`. It targets the existing supervisor without the desktop caller dependency. Do not create a replacement chat or assume transport acceptance means handling is complete. |
| SQLite database/schema missing | Respect `CODEX_HOME` and detected numbered state databases. Set `CODEX_RELAY_STATE_DB` only for a known database; never modify Codex data to make a query pass. |
| Pending worktree setup | Use `codex_resolve` with the exact client ID until a real thread ID is known. Do not guess from titles or use a client ID as a thread ID. |
| Supervision blocked on project selection | Verify the exact intended project with `codex_projects({projectPath:"<intended absolute path>"})`, including catalogue omissions. Implicit selection uses only the verified supervisor `cwd`; do not copy the executor's project as a fallback. Explicitly selected projects may differ from the supervisor project, and exact requested chats can be read outside recent results. |
| Only a worktree is visible for an omitted project | A linked worktree cwd does not establish its project's root. Relay reads Git worktree metadata without guessing from path names. Use the original registered root, a verified root chat, a saved setup/creation receipt, or an exact saved target binding. Re-registration with the original watch ID reuses a full binding; assertions alone cannot invent an old unbound worktree's missing membership. |
| Project metadata is incomplete or the working directory is unexpected | Revalidate a saved worktree binding from its exact thread ID, `cwd`, and registered project even if recent/read metadata omits project membership. Any explicit disagreement still blocks. Project grouping, allowed source repositories, and `cwd` are distinct; moving a chat between projects does not prove its working directory changed. Use `expectedCwd` when a particular workspace is required. |
| Supervised reply cannot resolve its target | Use its saved `eventId` or `subscriptionId`; an optional `threadId` must match the persisted target. Event replies require an active unhandled event and active subscription. Titles are informational and may change after rename. Do not retry by selecting the title again. |
| Standalone `codex_reply` has no project | Include `threadId` and an explicit registered `projectPath` or `projectId`; add `expectedCwd` only when the actual workspace must be asserted. |
| Older active subscription has no target binding | `codex_reply` can attach a verified target with `eventId` or `subscriptionId` plus explicit `projectPath`/`projectId` and optional `expectedCwd`. Or re-register through `codex_watch` using the same `id`, exact original supervisor, and intended project. Either path preserves watch state/events; re-registration leaves inactive watches inactive unless authorized `enabled:true` is supplied. Do not retry completed `codex_supervise`; it returns the saved receipt. Legacy receipts stay historical and gain no fabricated target identity. |
| `codex_start` reports `needsAttention` after creating a chat | Use its exact returned `threadId` to inspect that same chat and resolve the reported identity issue. Do not start a replacement chat. Immediate successful starts return the validated target identity. |
| `codex_watch` lacks project identity | Supply an explicit registered `projectPath` or `projectId`, even when the watched thread is already known. |
| Watch event stays `pending` | Read `codex_watches` polling errors and event delivery error/backoff. Verify the selected supervisor identity, desktop availability, or live Claude channel/CLI. Definitely unsent delivery retries automatically. |
| Watch event stays `delivered` | Host transport accepted it, but handling is not acknowledged. Retrieve the event in that exact supervisor and check whether its actions already happened. Acknowledge `rearm` or `complete` after handling. Do not blindly redeliver. |
| Compact wake arrives | Call `codex_event_context` with its exact `eventId`. The notification intentionally omits reports and repeated instructions; do not read the same event body through both history and status by habit. |
| `codex_event_context` or `codex_event_report` is unknown | Update the installed source through the normal update flow and let this supervisor's MCP connection load the updated tools and initialization instructions. Do not invent a replacement event or remove durable state. |
| Context returns `skip`, `reconcile`, or `retryStatus` | Skip already handled work; reconcile uncertain prior actions with receipts; retry status when the host is unavailable. A captured preview is not current task state. Read the returned action rather than treating every notification as new work. |
| Context reports a truncated goal or insufficient preview | Use `codex_event_report` only for the needed detail. Read `section:"goal"` before a completion decision when criteria were truncated. Default reports target the original event turn; `section:"snapshot"` is the captured event data. |
| Report is paged, changed, or `complete:false` | Follow `nextOffset` and carry `reportHash` to detect changes between pages. Restart pagination if the hash changes. An incomplete captured excerpt is not proof of a full report; never substitute a different latest turn. |
| Watch event is `uncertain` | The host may already have received or acted on it. Inspect receiving session, outgoing receipts, and target state. Use `codex_watch_ack` action `retry` only after deciding explicit redelivery is appropriate. |
| Claude channel is disconnected | An ordinary MCP connection does not enable notifications. Start the authorized development channel with the explicit host flag and bind the actual session via `codex_channel_bind`; keep the session running. Closed-session unattended work needs the explicit resume adapter. |
| Claude session ID unavailable | Run installed CLI `host` in that supervising Claude session's shell and read `CLAUDE_CODE_SESSION_ID`. Do not select the latest transcript or generate a replacement ID. |
| Claude resume cannot start/authenticate | Verify its real executable, original absolute cwd, saved session, and normal Claude authentication. The adapter uses event-scoped MCP tools and does not bypass permissions. A documented busy-session refusal retries as unsent; use a live channel while actively using the same session. |
| Claude processed an event but exited with an error | Treat outcome as uncertain. Read the selected session/event and receipt before retrying; some actions may already have happened. Fake-host tests do not prove acceptance for the installed Claude CLI version. |
| Structured answer fails or lacks an owning Codex window | The MCP reply needs card-aware desktop IPC to close questions. It does not forward structured answers as an ordinary delegated message. Open/focus only with user-authorized `allowOpen:true`; otherwise report the actual delivery error. |
| Ordinary message cannot reach its desktop owner or input protocol | Ordinary messages require normal desktop start/steer IPC. Preserve the saved target and request ID, report the actual readiness/delivery error, and do not fall back to delegated messaging or create a replacement chat. Opening/focusing needs user-authorized `allowOpen:true`. |
| Model capacity failure leaves a resumed chat in `systemError` | Ordinary input starts a new turn on that same executor with inherited settings. Relay does not reject this state locally or match the model's error wording to decide input eligibility. Check receipts and status, then make bounded retries with backoff within the existing task and model choice. An unconfirmed submission, a still-resuming or unloaded session, or uncertain delivery still blocks automatic resending. Do not require a manual app Retry click solely because of `systemError`. |
| New supervised chat exists but work has not started | Native desktop creation receives the work task and acceptance criteria in its first prompt. Pending worktree setup or a later setup failure may still prevent readiness. Inspect saved setup and delivery receipts for the same request and exact chat. Creation success alone does not establish that work started; do not create a replacement. |
| First message in an automatically created executor has host attribution | Native `create_thread` may retain the host's own attribution that the message came from another ChatGPT chat. This is within the accepted boundary. Its body contains only the task and finish condition in normal conversation text, without Relay supervision, source narration, or authorization explanations. Follow-up start/steer IPC submits direct work input. See the repository ordinary-creation research note for the distinction between the supported body boundary and optional removal of all host attribution. |
| Executor context contains old supervision details | Follow-up messages contain only supplied work text, and shared MCP initialization no longer assigns a supervisory role. Native automatically created chats may retain the accepted host attribution on their first message. Existing history and an already loaded MCP connection retain their earlier context. Use a clean execution chat when requested; do not silently replace an existing bound target. |
| `Codex app tool request failed` on status/wait | Some desktop versions reject externally relayed `wait_threads`. Status and wait fall back automatically to `read_thread`, then to a bounded session-log tail (`source` field). If status still fails, run `doctor`; do not grep or read session logs directly. |
| Message timeout/disconnect | Retain the error's `requestId`; inspect `codex_delivery` and `codex_status` before retrying. Reuse the same ID and identical input for a retry. A new ID can duplicate a prior effect. |
| Reply receipt says sent, but recipient handling is unclear | Read the receipt's target identity and inspect that same task or event. Tool delivery success does not prove the recipient consumed or handled the message. Keep retries bound to the saved thread, project, and `cwd`. |
| Executor repeats an authorization question | Distinguish a routine decision within the saved task from a new user approval scope or an actual host rejection. Send a concrete work decision for routine questions; request new scope once in the supervisor. Keep authorization history and sources in supervisor/internal records. If the host rejects the operation, report its stated requirement without promising that message delivery passed approval or trying another phrasing/sender. |
| An authorized fix involves a library outside the executor project | Keep the bound executor by default and send the exact external paths, edits, and checks as work instructions. Recipient project identity is not the editable-file scope. Do not require adding the library to a project or creating another chat solely because its path is external. Use the host's normal permission-request path when needed; an actual denial or unavailable approval mechanism remains a blocker. |
| A separately requested new executor cannot confirm its project | This is a native new-chat setup constraint, not proof that an existing executor lacks permission to edit the library. Preserve the user's selected new-chat request and report its precise prerequisite. Do not automatically substitute another project or executor. |
| Project discovery fails with a connection error or invalid CLI option | Do not interpret the failure as an absent project or ask the user to add folders. Check the installed CLI help for valid arguments; run doctor for bridge connectivity and follow its diagnostic state before retrying discovery. Neither failure establishes a filesystem permission denial. |
| Intended project is absent from `list_projects` | Call `codex_projects` with the intended absolute `projectPath` (or exact known `projectId`), or pass it to preflight/supervise directly. The shared resolver checks existing local chat IDs with `read_thread` and verifies their project membership and actual directory. Do not create a substitute project/chat or use an unrelated listed project. Conflicting evidence and ambiguous directories still block; ID-only discovery with multiple workspaces needs an explicit intended path. |
| Older plain-thread reply receipt is incomplete | Retry identical arguments and `requestId` only after an active subscription verifies or repairs the target binding. Only pending writes resume; uncertain writes remain blocked. If all writes were delivered and only final receipt creation failed, identical retry reconstructs the receipt without desktop/current-event checks or sending, even after event acknowledgment or subscription removal. Historical receipts do not gain invented target identity. |
| Interrupted readiness or target inspection | Retry identical input and `requestId`. These read-only stages can repeat after a process crash; this does not permit replaying an uncertain creation, answer, or instruction. |
| `requestId` used for different input | Use a separate ID for a distinct intended operation, such as event-ID `:answer` versus `:followup`. Do not replace an uncertain request merely to bypass the guard. |
| Edited configuration/Skill/startup conflict | Preserve the edit and report its exact path/entry. Resolve the intended migration before updating/uninstalling. Do not delete an unrelated integration. |
| Watcher stopped intentionally | `service stop` preserves subscriptions and writes a stop marker. Use `service start` to clear it and resume; reinstall/startup alone must not be represented as proof of host delivery. |
| Unsupported OS/runtime | Windows is the only platform tested with a live desktop. On macOS/Linux, report the actual `doctor` result as untested-platform evidence; an unreachable `$CODEX_HOME/ipc/ipc.sock` means the desktop is not running or its layout differs. `invalidSocketPath` means `CODEX_RELAY_HOME` is too long for a Unix socket. There is no cloud support. If a bundled runtime moved, rerun installation with its verified absolute `--runtime` path. |

`CODEX_RELAY_HOME` selects Relay state/runtime; `CODEX_HOME` selects Codex data/config; `CODEX_RELAY_STATE_DB` selects a known state database. `CODEX_RELAY_PIPE`, `CODEX_RELAY_IPC_PIPE`, and `CODEX_RELAY_DAEMON_PIPE` are advanced adapter/test overrides, not values to guess. Preserve `watches/state.json` and `outgoing/` during recovery. No automatic pruning removes their deduplication history.
